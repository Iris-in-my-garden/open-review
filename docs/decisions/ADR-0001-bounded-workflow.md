# ADR-0001：固定有界工作流，不做自由 Agent

- 状态：Accepted
- 日期：2026-10
- 影响版本：workflow 13 nodes / `max_steps=32`
- 相关代码：`src/openreview/review/workflow.py`、`services/review_executor.py`

## 上下文

Code Review 的阶段相对稳定：取 PR、准备仓库、解析 diff、triage、检索、审查、校验、报告、发布。真正需要动态决策的只有 triage、维度选择、verifier 回炉和失败兜底。

自由 Agent 会带来：

- 不可复现的执行路径；
- 不可预估的调用数与成本；
- 难以测试的条件分支；
- 难以向用户解释“为什么这步没跑”。

## 决策

用 `BoundedWorkflow` 顺序执行 13 个固定节点，每个节点带 `enabled` 谓词；条件边全部由代码定义，模型不能增加工具或自循环。

## 备选方案

| 方案 | 放弃原因 |
|---|---|
| LangGraph / 通用 Agent 框架 | 引入重依赖，但动态性收益不足以抵消可测试性损失 |
| 模型自主规划工具调用 | 成本与路径不可控，失败不可解释 |
| 纯函数管道（无状态对象） | 无法承载预算、trace、降级原因与中间结果 |

## 后果

正面：

- 每条路径都能回答“何时执行、消耗多少预算、失败后怎么办”；
- 节点级测试、trace、进度、跳过原因都自然成立；
- 评测可以固定同一组节点，只改变检索/verifier 变量。

负面：

- 扩展新能力需要改代码，不能靠模型临时“发明工具”；
- 节点顺序与 `_PROGRESS_STEPS` 需要手动保持同步。

## 证据

- `BoundedWorkflow.run` 在节点异常时记录 `status="error"` 并重新抛出；
- `max_steps=32` 防止节点表失控；
- 338 tests 覆盖节点跳过、失败、预算与 outcome。

## 复审条件

当出现“必须由模型决定下一步调用哪个工具”的场景（例如多轮代码探索），且能用离线评测证明收益大于成本时，再引入受控的动态分支。
